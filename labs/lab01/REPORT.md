# Лабораторная работа № 1. Система контроля версий Git

## Цель
Освоить создание репозитория, работу с индексом, ветками, Pull Request, конфликтами слияния и отменой опубликованных изменений.

## Ход работы
Создан публичный репозиторий [YaGi4/nids-service-bakhtin](https://github.com/YaGi4/nids-service-bakhtin). Шаблон проекта зафиксирован отдельным коммитом `abc3c4e`; сведения об авторе — коммитом `fdd89df`. До `git add AUTHOR.md` файл отображался как `?? AUTHOR.md`, после — как `A  AUTHOR.md`: файл перешёл из рабочего каталога в индекс. README дополнен двумя коммитами в `feature/readme` и слит через [PR № 1](https://github.com/YaGi4/nids-service-bakhtin/pull/1).

```text
$ git status --short
?? AUTHOR.md
$ git add AUTHOR.md
$ git status --short
A  AUTHOR.md
```

Для конфликта созданы ветки `exp/alpha` и `exp/beta`, изменявшие одну строку README. После слияния первой ветки вторая дала конфликт:

```text
<<<<<<< HEAD
Сервис анализирует сетевые соединения как обычные или потенциально вредоносные...
=======
Сервис обнаруживает угрозы в сетевых соединениях как обычные или потенциально вредоносные...
>>>>>>> exp/beta
```

Оставлена единая формулировка: «Сервис анализирует сетевые соединения и выявляет потенциальные угрозы». Временный плохой коммит `d5acf48` удалял раздел README; `git revert` создал компенсирующий коммит `d3caf02`.

Проверка исключений: `artifacts/*`, `data/*.csv`, `.env`, `.venv/` и `__pycache__/` перечислены в `.gitignore`. Git не начинает игнорировать уже отслеживаемый файл после записи правила: требуется `git rm --cached путь`, затем коммит.

## Ответы на контрольные вопросы
1. Коммит — снимок дерева файлов с метаданными и ссылками на родителей, а не отдельная копия одного файла.
2. Индекс позволяет включить в коммит только законченную часть изменений, оставив экспериментальные правки в рабочем каталоге.
3. Ветка — лёгкий указатель на коммит; копирование всех файлов при её создании не требуется.
4. В коммит попадёт содержимое файла на момент `git add`; более позднее изменение останется в рабочем каталоге.
5. Большой датасет увеличит каждое клонирование и хранение истории; удаление из текущей версии не удалит его старые объекты. Для данных подходят внешнее хранилище, DVC или LFS.
6. `<<<<<<< HEAD` обозначает текущую сторону, `=======` разделяет варианты, `>>>>>>>` показывает присоединяемую ветку.
7. `revert` добавляет обратный коммит без переписывания истории. `reset` перемещает указатель ветки; принудительная отправка такой истории нарушает работу коллег.

## Возникшие затруднения и устранение
Новый репозиторий GitHub первоначально получил ветку `feature/readme` как ветку по умолчанию, поскольку она была отправлена первой. Через API GitHub ветка по умолчанию изменена на `main`, после чего временная ветка удалена. Локальный проект изначально не содержал `.git`, поэтому история создана с импортом шаблона.
