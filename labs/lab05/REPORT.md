# Лабораторная работа № 5. Docker Compose

## Цель
Развернуть API и PostgreSQL одной конфигурацией, обеспечить готовность базы, сохранение данных, автоматическое создание схемы и запуск нескольких копий API.

## Ход работы
`compose.yaml` описывает два сервиса: `db` на `postgres:16-alpine` и `api`, собираемый из Dockerfile. Пароль берётся из игнорируемого Git файла `.env`; структура переменных опубликована в `.env.example`. Внутри сети Compose API использует имя `db`, а не `localhost`: последнее обозначало бы сам контейнер API. Зависимость `condition: service_healthy` ждёт успешного `pg_isready`. SQL-миграции подключены в `/docker-entrypoint-initdb.d` и выполняются на пустом томе.

```text
$ docker compose up -d --build
project-db-1    Up (healthy)
project-api-1   Up
$ curl -s http://localhost:8000/health
{"status":"ok","model_loaded":true,"model_version":"0.1.0"}
$ docker compose exec -T db psql -U nids -d nids -c '\dt'
public | predictions | table | nids
```

На 500 запросах в журнале было 500 строк. После `docker compose down` и повторного `up` их осталось 500. После `docker compose down -v` и `up` таблица была создана автоматически, но число строк стало 0. Следовательно, обычный `down` сохраняет именованный том, `down -v` удаляет его.

Для трёх копий API использован `compose.scale.yaml`, снимающий публикацию фиксированного порта хоста. В противном случае все контейнеры пытаются занять один `8000` на хосте.

```text
$ docker compose -f compose.yaml -f compose.scale.yaml up -d --scale api=3
$ docker compose -f compose.yaml -f compose.scale.yaml ps
project-api-1  Up  8000/tcp
project-api-2  Up  8000/tcp
project-api-3  Up  8000/tcp
project-db-1   Up (healthy)  5432/tcp
```

Эксперимент с падением API до введения healthcheck не дал ожидаемого падения: код ЛР4 специально перехватывает ошибку БД и возвращает предсказание. При остановленной базе зафиксирован фактический лог `Не удалось записать предсказание в PostgreSQL`, затем `psycopg.OperationalError`, а HTTP-ответ остался 200. Стартовая гонка здесь проявляется в потере записи журнала, а не в падении API. Это более точное описание поведения данного проекта.

Проверка на чистом локальном клоне ветки `feature/lab05` выполнена в `/tmp/nids-clean`: после `cp .env.example .env` команда `docker compose up -d --build --wait` завершилась успешно; `/health` вернул `status=ok`, таблица `predictions` существовала и содержала 0 строк. Дополнительных ручных действий для схемы и модели не потребовалось. Развёртывание на машине однокурсника и соответствующие затруднения не проверялись: доступа к чужой машине не было.

## Ответы на контрольные вопросы
1. Compose хранит конфигурацию нескольких сервисов, сети, тома и зависимости в версионируемом файле; набор `docker run` трудно повторить без ошибки.
2. В общей сети сервисы обращаются друг к другу по DNS-именам `db` и `api`.
3. Обычный `depends_on` ждёт запуска контейнера, `service_healthy` — успешной проверки готовности.
4. Плавающая гонка зависит от времени старта процессов, поэтому может не проявиться при локальном тестировании и воспроизводится нерегулярно.
5. `down` удаляет контейнеры и сеть, `down -v` дополнительно удаляет именованные тома.
6. `.env.example` документирует обязательные ключи и даёт воспроизводимую отправную точку без публикации рабочего секрета.
7. API не хранит своё состояние между запросами. База содержит единственный журнал; независимое копирование базы привело бы к расходящимся данным и требует репликации/координации.
8. Публикация порта БД расширяет поверхность атаки; внутренней сети Compose достаточно для связи API с БД.

## Возникшие затруднения и устранение
Сразу после первого `docker compose up` команда `curl` вернула ошибку соединения: `service_healthy` проверял только БД, а не готовность Uvicorn. Через несколько секунд `/health` стал отвечать. В итоговую конфигурацию добавлен healthcheck API, а README использует `docker compose up --wait`. Масштабирование с фиксированным host-портом невозможно, поэтому для демонстрации добавлен `compose.scale.yaml`.
