# Лабораторная работа № 3. Контейнеризация сервиса

## Цель
Собрать самодостаточный образ сервиса, сократить объём контекста и время пересборки, убрать привилегии root при работе API.

## Ход работы
Образ `nids-service:v1` собран из одноэтапного Dockerfile, `nids-service:v2` — из двухэтапного. Оба используют `python:3.12-slim`, обучают модель при сборке и запускают Uvicorn на `0.0.0.0:8000`. Финальный образ содержит зависимости и модель, но не CSV. Команда `docker run --rm nids-service:v2 whoami` вывела `nids`. `/health` вернул `{"status":"ok","model_loaded":true,"model_version":"0.1.0"}`.

Размер файлов в рабочем каталоге, потенциально входящих в контекст, измерен обходом файлов: до правил `.dockerignore` — 417 430 702 байт и 12 511 файлов; после — 41 907 байт и 24 файла. Исключены `.git`, `.venv`, CSV, локальные артефакты, `.env`, кэши, тесты и отчёты. BuildKit при этом фактически передавал только затребованные `COPY` файлы, поэтому его строка `transferring context` не равна полному размеру допустимого контекста.

Оптимизированный Dockerfile сначала копирует `pyproject.toml` и ставит внешние зависимости; только затем копирует `src` и ставит пакет `--no-deps`. При правке исходного кода дорогой слой зависимостей остаётся в кэше. Измерения командой `/usr/bin/time -p docker build` на одном Mac: первая сборка v1 — 83,17 с, пересборка v1 после правки описания API — 83,03 с, пересборка оптимизированного v2 после той же правки — 44,53 с. Размеры по `docker image inspect`: v1 — 170 270 503 байта, v2 — 167 673 651 байт. Экономия размера невелика, потому что основную долю дают одинаковые зависимости Python; по `docker history` слой их копирования занимает около 421 МБ без сжатия.

```text
$ docker run --rm nids-service:v1 whoami
root
$ docker run --rm nids-service:v2 whoami
nids
$ docker run --rm -v "$(pwd)/artifacts:/models:ro" -e MODEL_DIR=/models nids-service:v2 python -c 'from nids.api import load_model; print(load_model())'
True
```

Модель можно вынести из образа, задав `MODEL_DIR=/models` и смонтировав каталог `artifacts` только для чтения. Вшитая модель даёт самодостаточный артефакт, но обновление требует новой сборки. Том позволяет обновить модель отдельно, но создаёт внешнюю зависимость запуска.

Файл `.env` исключён до передачи контекста: удаление секрета последующей инструкцией `RUN rm` не удалило бы его из предыдущего слоя образа. Команда `docker history nids-service:v2` использована для оценки слоёв.

## Ответы на контрольные вопросы
1. Образ — неизменяемый шаблон файловой системы и команды запуска; контейнер — его выполняемый экземпляр. Записи во внутренний слой контейнера исчезнут после удаления без тома.
2. Контейнер разделяет ядро хоста и не запускает отдельную гостевую ОС; поэтому старт обычно быстрее старта ВМ.
3. Контекст — файлы, доступные Docker при сборке. `.dockerignore` исключает ненужные файлы и секреты.
4. Ранние стабильные инструкции дают повторное использование кэшированных слоёв при частых изменениях кода.
5. Да, секрет остаётся в старом слое образа и может быть извлечён из истории слоёв.
6. Многоступенчатая сборка оставляет инструменты сборки в промежуточном образе и переносит в итоговый только нужные файлы.
7. `127.0.0.1` внутри контейнера доступен только самому контейнеру; `0.0.0.0` принимает соединения через опубликованный порт.
8. `latest` меняет содержимое без изменения Dockerfile, лишая сборку воспроизводимости и предсказуемости обновлений.

## Возникшие затруднения и устранение
В исходном двухэтапном Dockerfile пакет и все зависимости устанавливались после копирования `src`; изменение одной строки снова запускало установку. Инструкции разделены: зависимости ставятся до `COPY src`, сам пакет — после. Файл `.dockerignore` уменьшил объём доступных сборке файлов. Проверка поведения Docker BuildKit показала, что он передаёт только файлы, указанные в `COPY`, поэтому отдельно приведён размер всего допустимого контекста.
